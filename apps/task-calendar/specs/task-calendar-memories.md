# 思い出シェアカレンダー（Phase 1）

- 対象アプリ: Task Calendar（TaskARE）
- 状態: Phase 1 実装済み（v86）
- 関連仕様: [共有カレンダー（Firebase Phase B）](task-calendar-firebase-sync.md)

## 1. 背景と目的

既存の共有カレンダーは「**これから**の予定を合わせる」道具である。一方で、友人・家族・仕事仲間と「**終わったこと**」を持ち寄りたいという要望がある（setlog のような、仲間内で記録を共有する使い方）。

このアプリは**個人利用がメイン**であり、共有相手が増えるほど自分の「日・週・時間・月」が汚れるのは避けたい。そのため、予定を合わせる共有と思い出をためる共有を**別の種類**として扱い、思い出はふだんの画面に出さないことを既定とする。

## 2. 決めたこと

### 2.1 カレンダーに「種類」を持たせる

共有ドキュメント `shared/{招待コード}` に `kind` を持たせる。

| kind | 意味 | ふだんの画面（日・週・時間・月・年） | 専用タブ |
|---|---|---|---|
| `plan`（既定・従来） | 予定を合わせる共有 | 出る | — |
| `memory` | 思い出をためる共有 | **出ない**（端末ごとの設定でONにできる） | 「思い出」タブに出る |

- `kind` を持たないドキュメント（v85以前に作られたもの）は `plan` として扱う（後方互換）。
- ふだんの画面に出すかどうかは `db.settings.memShowInCal[コード]`。`settings` は同期しないので**この端末だけの選択**であり、相手の画面には影響しない。
- 思い出カレンダーが1つも無いあいだは「思い出」タブ自体を出さない（自分用がメインという前提を崩さないため）。タブは「表示する項目」からも隠せる。

### 2.2 思い出1件の中身

思い出は既存の予定・タスクそのもの（`db.tasks` / `db.events` に `calendarId='s:コード'`）。既存の同期・編集・削除・色・フチがそのまま効く。追加したフィールドは3つだけ。

| フィールド | 形 | 用途 |
|---|---|---|
| `photos` | `[{ id, w, h, b }]` | 写真の**メタ情報のみ**（実体は別ドキュメント）。1件4枚まで |
| `stamps` | `[{ uid, name, e, at }]` | 1人1個のスタンプ（押し直しで変更、同じものを押すと取り消し） |
| `comments` | `[{ id, uid, name, t, at }]` | ひとことコメント。1件30件まで（古いものから落ちる） |

- **セット記録**（ライブの曲順・旅行で行った場所）は既存の「詳細（`subs`）」をそのまま使う。番号つきリストとして表示する。
- **リンク**（YouTube等）も既存の `link` をそのまま使う。
- 表示名は `settings.userName` → Googleの表示名 → メールのローカル部 → 「わたし」の順で決める。

### 2.3 写真の置き場所（無料枠で完結させる）

**Cloud Storage は使わない。** 新しいFirebaseプロジェクトでは Cloud Storage の利用に Blaze（従量課金）プランが必要で、「予期しない課金は避ける」という前提に合わない。写真は Firestore に入れる。

- 保存先は `shared/{招待コード}/photos/{写真ID}`、**1枚 = 1ドキュメント**。
  - 本体ドキュメント（`shared/{コード}`）は変更のたびに `tasks`/`events` を丸ごと書き換えるので、そこに写真を入れると1MiBのドキュメント上限と書き込み量をすぐ食いつぶす。
- 中身は `{ bin: Firestore Blob, w, h, b, at, by }`。base64文字列ではなく Blob（バイナリ）で持つ（base64は約33%膨らむため）。
- クライアント側で**長辺1280pxへ縮小 → JPEG画質を 0.82→0.42 の順に落として1枚240KB以内**に収める。実測: 4000×3000・518KB の写真 → 1280×960・110KB（約0.35秒）。
- 一度読んだ写真は端末の IndexedDB（既存の `tc-images` ストア、キー `mp:{写真ID}`）に残す。2回目以降は読み取り回数も通信も使わない。

#### 上限（「少量でベストを濃く残す」方針の実装）

| 上限 | 値 | 理由 |
|---|---|---|
| 1件あたり | 4枚 | ベストだけを選ばせる |
| 1カレンダーあたり | 100枚 | 100枚 × 約240KB ≒ 24MB。無料枠の保存容量1GiBに対して十分に小さい |
| 1枚 | 240KB | 上記の計算根拠 |

設定の「思い出シェアカレンダー」に `写真 n/100枚・約xxMB` を常に出し、使用量が見えるようにする。

#### 置き去りになる写真の掃除

- オーナーがカレンダーを削除するとき、本体ドキュメントを消す前に写真ドキュメントも消す（Firestoreは親を消してもサブコレクションは残るため）。
- 予定の削除は「元に戻す」があるので、そのタイミングでは写真を消さない。代わりに設定の「**使っていない写真を片づける**」で、どの思い出からも参照されていない写真をまとめて削除する。

### 2.4 権限

既存の共有カレンダーと同じ（オーナー／書き込める＝editor／見るだけ＝viewer）。viewer は写真・スタンプ・コメントを追加できず、UIからボタンを出さない。

### 2.5 自分のカレンダーへの控え（ミラー）

写真・スタンプ・コメントは共有カレンダー側の持ち物なので、控え（`MIRROR_SKIP`）には写さない。共有をやめると本文・詳細は自分の予定として残るが、写真は残らない。

## 3. Firestoreセキュリティルール（追加分）

親の `shared/{calId}` と同じ「招待コードを知っている＝アクセスできる」モデルに合わせる。

```
match /shared/{calId}/photos/{photoId} {
  allow read: if request.auth != null;
  allow write: if request.auth != null;
}
```

**このルールを追加しないと写真の保存が `permission-denied` になる。** その場合はアプリ側で「Firebaseのルールに photos の許可を追加してね」とトーストで案内する。

## 4. 画面

### 「思い出」タブ（`#scr-memories`）

- 思い出カレンダーが2つ以上あるときだけ、上部に切り替えチップを出す。
- 「＋ 思い出を追加」→ 編集シート（カレンダーは選択中の思い出カレンダーに固定、日付は今日。過去日に変えて使う）。
- 本体は**新しい順**のタイムライン。年月で区切る。
- 1枚のカード = 日付・曜日・タイトル（タップで詳細）／時刻・場所・誰と／写真（1枚=4:3、3枚=左に大きく1枚+右に2枚、2・4枚=2×2）／セット記録／リンク／メモ／スタンプ／コメント＋入力欄。

### 編集シート

`#f-photos-wrap` は**思い出カレンダーを選んでいるときだけ**出る。写真は選んだ時点では端末内で圧縮するだけで、**保存ボタンを押したときにアップロードする**（キャンセルしても置き去りが出ない）。

### 設定

「連携・同期 → 思い出シェアカレンダー」。作成・招待コードのコピー・「ふだんのカレンダーにも出す」・使用量・メンバーの権限・写真の片づけ・削除。参加は既存の「共有カレンダー → 招待コードで参加」から両方の種類に参加できる。

## 5. Phase 1 に入れていないもの（次の候補）

- 「去年の今日」の再浮上
- カレンダーの表紙（カバー写真・絵文字）
- 写真の本物のアップロード（Cloud Storage・Blazeプランが必要）
- 未読バッジ、メンバー一覧の表示名
